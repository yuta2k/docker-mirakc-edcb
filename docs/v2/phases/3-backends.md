# フェーズ 3: 複数バックエンド

## 目的

複数の mirakc / Mirakurun につなげるようにする。BonDriver をホスト名に対応させ、チューナー数を自動で設定する。チャンネル定義の自動化はフェーズ 4。

関連する方針: `decisions.md` の A5、B3、C1、C4、E1。仕様: `design.md` の 3.2、5.1、7 章。

## 先に確認すること

`facts.md` の U9、U10 を確認する。U10 で「EDCB 側は再選局しない」と分かった場合は、BonDriver に再接続を入れるかどうかをユーザに相談する(このフェーズの範囲を広げる判断になるため)。

## 作業

### 1. BonDriver の修正

修正は、BonDriver のソースを一時ディレクトリに clone して行い、`git format-patch` で `edcb/patches/bondriver/` に出力する。Dockerfile で `git am --3way` を使って当てる。ユーザがフォークを作成済みなら、フォークのブランチに commit し、Dockerfile の取得元をフォークに変える(push はユーザの指示を待つ)。

1 パッチ 1 修正にする。

- **ホスト名対応**: `MirakcConnectHttp` で `getaddrinfo` を使う。**接続のたびに**名前解決する(コンストラクタで 1 回だけ、にしない。コンテナの IP が変わっても追従するため)。IPv4 のみでよい。解決に失敗したら接続失敗として扱い、落ちないこと。
- **固定長バッファ**: 応答ヘッダ(512 バイト)と本体(128KB)へのコピーに長さの確認を入れる。本体は必要に応じて拡張するか、上限を超えたら失敗として扱う。
- **再接続**(U10 の結果、2026-10-05 にユーザと合意して追加): 受信スレッドが切断やエラーを検知したら、間隔を空けて同じチャンネルへ再接続を繰り返す。`SetChannel`、`CloseTuner`、デストラクタで止まること。再接続のたびに名前解決する(上のホスト名対応による)。
- 上記以外の変更(整形、リファクタリング)はしない。

### 2. 接続先の設定

- `design.md` の 3.2 の環境変数を実装する。互換(`MIRAKC_ADDRESS` など)と、未指定時の既定(`http://mirakc:40772`)を含む。
- フェーズ 2 で残した「entrypoint での名前解決」を削除する。

### 3. バックエンド情報の取得

- `design.md` の 5.1 の手順 2。取得、保存、失敗時の代替。
- 接続先が複数あっても、待ち時間の合計が上限を超えないこと(並行に取得するか、接続先ごとの上限を分ける)。

### 4. BonDriver の生成とチューナー数

- `design.md` の 7 章。
- このフェーズでは ChSet4 を作らないので、新しい接続先の BonDriver は EDCB からまだ見えない。**既存の ChSet4 があるもの(従来の `BonDriver_LinuxMirakc*.so`)が、これまでどおり動くこと**を確認する。

### 5. テスト用の偽サーバ

- `edcb/tests/` に、Mirakurun API の `/api/tuners`、`/api/channels`、`/api/status` を固定データで返す小さな HTTP サーバを作る(Python 標準ライブラリ)。
- 固定データは、チューナー構成の違う数パターンを用意する(両対応のみ / 地上波専用 + 衛星専用 / 混在 / `SKY` を含む)。
- pytest から起動して、取得、分類、ini への書き込みを確認する。

### 6. そのほか

- `edcbctl backends` を作る。
- `compose.yml` から `MIRAKC_ADDRESS` / `MIRAKC_PORT` を削除する(未指定時の既定で同梱の mirakc につながる)。
- `edcb.env-sample` に接続先の例を足す。

## 受け入れ条件

- [ ] BonDriver のパッチが当たり、ビルドが通る
- [ ] 偽サーバをホスト名で指定して、`EpgDataCap_Bon -d BonDriver_LinuxMirakc.so` が偽サーバの `/api/channels` に到達する(BonDriver のデバッグ出力か、偽サーバのアクセスログで確認)
- [ ] 接続先を 2 つ指定すると、`/usr/local/lib/edcb/` に 6 組の `.so` と `.ini` ができ、それぞれの ini が正しい接続先を指す
- [ ] 2 つの接続先の BonDriver で、それぞれ別の偽サーバに到達する(別名のコピーごとに別の ini が読まれることの実証)
- [ ] 受信中に偽サーバが接続を切ると、BonDriver が同じチャンネルのストリームを要求し直す(偽サーバのアクセスログで確認)
- [ ] `design.md` の 7.2 の分類が、固定データの全パターンで期待どおりになる
- [ ] セクションが無いときだけ `Count` が書かれる。既にあるときは警告だけで、値は変わらない
- [ ] `TUNERS` を明示すると、`Count` が毎起動で上書きされる
- [ ] 接続先の 1 つに届かなくても、EpgTimerSrv が起動し、届く接続先の設定は行われる。全体の待ち時間が上限に収まる
- [ ] 2 回目以降の起動では、届かない接続先に保存済みの情報が使われる
- [ ] 不正な接続先名(`T`、`S`、アンダースコア入り、小文字)は無視され、警告が出る
- [ ] `MIRAKC_ADDRESS` / `MIRAKC_PORT` だけを指定した従来の構成が、そのまま動く
- [ ] pytest がすべて通る

## 実機確認の依頼

次の手順をまとめて、ユーザに依頼する。

- 同梱の mirakc にホスト名(`mirakc`)でつながり、従来の ChSet4 のまま録画・視聴できるか
- 外部の mirakc / Mirakurun を 2 つ目の接続先として指定し、`edcbctl backends` に正しいチューナー数が出るか
- mirakc コンテナを再作成して IP アドレスが変わったあとも、EDCB を再起動せずにつながるか

## 実施記録

### 先に確認したこと

- U9: 前提どおり(`facts.md`)。
- U10: EDCB も BonDriver も選局し直さない(`facts.md`)。ユーザと相談し、再接続をこのフェーズに入れた(`decisions.md` の A5)。

### 行ったこと

- BonDriver のパッチ 3 本(`edcb/patches/bondriver/`)。ホスト名(接続のたびに `getaddrinfo`、IPv4)、応答バッファの長さの確認(ヘッダ 512 バイト、本体は 16 MiB まで拡張)、受信中の切断からの再接続(1、2、4 秒、以降 5 秒ごと。`SetChannel` / `CloseTuner` で即座に止まる)。
- 接続先の環境変数、取得と保存、BonDriver の生成、チューナー数(`edcb_provision/backends.py`)。`edcbctl backends`。
- 偽の Mirakurun(`edcb/tests/fake_mirakurun.py`)。シナリオは `dual`(両対応のみ)、`split`(地上波専用 + 衛星専用)、`mixed`(混在。BS のみ、CS のみ、GR + CS を含む)、`sky`(`SKY` を含む)。ストリームを途中で切る、応答を遅らせる、のオプションを持つ。
- 結合テスト `tests/integration/phase3.sh`(T30〜T39)。`scripts/check.sh` が、`# shellcheck shell=` で始まる読み込み用のスクリプトも shellcheck にかけるようにした(`lib.sh`、`phase*.sh` が対象外だった)。
- `compose.yml` には、フェーズ 2 の時点で `MIRAKC_ADDRESS` / `MIRAKC_PORT` が無かった。変更なし。

### 設計から変えた点・決めた点

`design.md` の 3.2、5.1、7.1、7.3 に書き足した。要点:

- `DEFAULT` の URL を省略すると同梱の mirakc。`EDCB_BACKEND_DEFAULT_TUNERS` だけを書ける。
- `MIRAKC_ADDRESS` / `MIRAKC_PORT` は片方だけでもよい(v1 の entrypoint と同じ既定値を補う)。
- 生成した BonDriver の記録は、状態ファイルではなく `/usr/local/lib/edcb/.edcb-provision.json`(コンテナ内のファイルのため)。
- 保存済みの接続先の情報は、URL が変わったら使わない。
- 取得は接続先ごとに並行。1 回の要求は 5 秒まで、全体は 30 秒まで。

### 検証

- BonDriver のパッチは、ホストでビルドした `.so` を小さなプログラムで読み込み、偽サーバに対して確認した(2026-10-05)。ホスト名 `localhost` で接続できる。サーバが 2 回ストリームを切っても、それぞれ約 1 秒で同じ URL を要求し直す。サーバを 8 秒止めても、4 回目で再接続する。再接続を待っている間の `CloseTuner` は 0.02 秒で終わる。名前を引けないホストでは `OpenTuner` が失敗するだけで落ちない。1.1 MB(3000 チャンネル)の `/api/channels` を読める。16 MiB を超える本体と 512 バイトを超えるヘッダは、失敗として扱われる。
- `scripts/check.sh`: すべて PASS(pytest 105 件。レビューでの修正後は 108 件)。
- `tests/integration/run.sh`(ユーザが実行、2026-10-05):
  - 1 回目(ビルドあり、`07a3270`): 24 件すべて PASS。ただし T34 は、作り直した偽サーバに Docker が同じアドレスを渡したので(`172.27.0.3 -> 172.27.0.3`)、アドレスの変化への追従を示せていなかった。空いたアドレスを別のコンテナで先に埋め、アドレスが変わらなければ FAIL にするよう直した(`ef83227`)。
  - 2 回目(`EDCBTEST_SKIP_BUILD=1`、`ef83227`): pass=22 fail=0 skip=2(T0 / T0b はビルドを省いたため SKIP)。T34 はアドレスが `172.27.0.3 -> 172.27.0.5` に変わったあとも、約 1 秒で同じチャンネルへ再接続した。
  - 主な結果: T35 では、届かない接続先(`192.0.2.1`、5 秒で打ち切り)があっても、起動から EpgTimerSrv の開始まで 7 秒だった。T38 では、v1 の変数と既存の ChSet4 で EDCB が BonDriver を一覧に出し、ChSet4 のサービスを選局して偽サーバに `GR/27` のストリームを要求した。

### コードレビューでの修正(2026-10-05)

`/code-review` の指摘 4 件(いずれも重大度は低)を直した(`31ec7e1`)。

- BonDriver: 停止の要求が再接続の `socket()` と `connect()` の間に来ると、`shutdown` が効かず、受信が続いて `CloseTuner` / `SetChannel` が終わらなくなりえた。再接続が成功した後にも停止の要求を確かめる(パッチ 0003)。
- 接続先名は 32 文字、ホスト名は 200 文字までにした。BonDriver はファイル名を `char[128]` にコピーし、ini を 1 行 255 バイトまでしか読まない。生成する ini の注釈の行も短くした。
- 壊れた HTTP 応答(`http.client` の例外)を、トレースバックと「timed out」ではなく、その理由で報告する。
- 生成した BonDriver の書き換えに失敗しても記録を残し、次の起動で再び書き換える(利用者のファイル扱いにしない)。

pytest は 108 件。修正後のパッチは、ホストでのビルドで再接続と停止を確かめた(停止の要求がすれ違うタイミングそのものは、狙って起こせないため試験していない)。修正後の結合テスト(ユーザが実行、ビルドあり、`4397afa`)は 24 件すべて PASS(T34 はアドレス `172.27.0.3 -> 172.27.0.5`)。

### 次のフェーズへの申し送り

- このフェーズでは ChSet4 を作らないので、新しい接続先の BonDriver は EDCB から見えない(`edcbctl backends` の `ChSet4` 列)。
- `edcbctl backends` の「スキャン以降のチャンネル構成の変化」は、スキャンの記録ができるフェーズ 4 で埋める。
- 接続先の保存済み情報(`.provision/backend-<名前>.json`)には、`/api/channels` の `type`、`channel`、`name` を並び順のまま入れてある。フェーズ 4 の分割とずれの検知に使える。
