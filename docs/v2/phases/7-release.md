# フェーズ 7: リリース

## 目的

v2 を利用者に届ける。フェーズ 6 までで、実装、文書、検証は揃っている。このフェーズで残っているのは、ユーザの判断が要る事項と、その判断を受けて行う作業。

2026-10-06 に、フェーズ 6 の残りをここに移した(ユーザの希望。フェーズ 6 を先に `v2` に入れるため)。ユーザがしばらく手元で使い、精査とドキュメントの整理をしてから着手する。

関連する方針: `decisions.md` の A4、D4、E2、「未決定」の「リリースの切り方」。

## ユーザが決めること

| 事項 | 材料 | 決まったら行う作業 |
|---|---|---|
| リリースのタグ名 | 文書は `v2.0.0` の形と仮定している。`release.yml` は semver のタグ(`v[0-9]+.[0-9]+.[0-9]+*`)だけを受け付ける | 違う名前なら、`Readme.md`、`Setup.md`、`docs/migration-v1-to-v2.md` の `v2.0.0` を直す |
| GHCR で配布イメージを公開するか | `phases/6-docs-release.md` の「公開の判断の材料」(EDCB と EMWUI に再配布条件の記載が無い。`facts.md` の F8) | 下の作業 2 |
| v1 の最後のコミットにタグを付けるか | v1 の最後のタグ `v1.0.4` には btrfs のパッチが入っていない。v1 の最後は `main` の `8f38425`。移行手順の「元に戻す」は、利用者が控えたコミットに戻す形なので、タグが無くても戻せる | 付けるなら、移行手順の末尾の `v1.0.4` をそのタグに直す |

## 作業

### 1. 手元での精査を受けた修正

ユーザが使ってみて見つけた点を直す。文書を変えたら `scripts/check.sh`(リンクの検査を含む)を通し、手順を変えたら `tests/integration/run.sh` の T60 / T61 を通す。

### 2. 配布イメージ(公開すると決めた場合)

- `compose.yml` の edcb に `image:` を足す(`design.md` の 2 章)。`build:` と両方を書いたときに、`docker compose up` が pull するのかビルドするのかを、先に確かめる(`pull_policy` の扱い)。
- `Readme.md` の「更新」に、配布イメージを固定のタグで使う方法を足す。`latest` と自動更新ツールを併用しないことは既に書いてある(`decisions.md` の E2)。
- `edcb/hwaccel/intel/Dockerfile` の `BASE_IMAGE` の既定値(`ghcr.io/…/edcb:latest`)と、`Setup.md` の「ハードウェアエンコード」の手順(今はローカルでビルドした `edcb-base:local` を使う)を見直す。
- 公開の操作(タグの push、パッケージを public にする)はユーザが行う。

### 3. リリース(ユーザが行う)

1. `v2` を `main` にマージする
2. タグを push する(公開する場合は `release.yml` がイメージを push する)
3. 定期チェック(`upstream-check.yml`)は `main` に入ってから動く。自動 PR で CI を動かすなら `UPSTREAM_CHECK_TOKEN` を登録する(`docs/v2/README.md` の「ユーザの作業が必要なもの」)
