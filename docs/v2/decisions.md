# 合意済みの方針

2026-10-04 にユーザと合意した内容です。**変更が必要になったら、実装を進めずユーザに確認してください。**

各項目の「理由」は、判断に迷ったときに方針の意図を汲むためのものです。

## A. 上流とビルド

### A1. EDCB は xtne6f 版のリリースタグを使う

- これまでの tkntrec 版(`my-build` ブランチの HEAD)から、`xtne6f/EDCB` の `work-plus-s-YYMMDD` タグに切り替える。
- 理由: Linux で動く部分の差は `CompatFlags` の扱いだけ(`facts.md` の F1)。xtne6f 版にはタグがあり、歴史改変があってもタグで固定できる。
- tkntrec 版の EpgTimerNW を使う利用者のため、`CompatFlags=4095` を既定で書き込む(B2)。

### A2. 固定はコミットまで行い、Dockerfile の ARG 既定値を唯一の定義場所にする

- EDCB はタグとコミットの両方、BonDriver と EMWUI はコミットで固定する。
- ビルド時に「タグが指すコミットが、固定したコミットと一致するか」を検査する。
- 理由: 利用者のビルド時に上流の HEAD を取ると、いつ壊れるか分からない。

### A3. パッチはこのリポジトリに置き、`git am --3way` で当てる

- btrfs 対策の 2 本(`edcb/patches/`)は維持する。失敗したらビルドを失敗させる(`|| true` で握りつぶさない)。
- xtne6f への上流提案は**保留**。行わない。
- btrfs パッチを小さくする案(判定をプロビジョニングに移す)は未決定。v2 では現状のまま持ち込む。

### A4. CI でビルドを検証し、EDCB イメージだけを GHCR で配布する

- mirakc イメージは配布しない(libaribb25 を同梱しているため)。ローカルビルドのまま。
- 実際に公開するかは、再配布条件の確認後にユーザが決める。エージェントは公開操作をしない。
- 定期実行で上流の新しいタグを検出し、パッチ込みでビルドが通れば固定を更新する PR を作る。

### A5. BonDriver_LinuxMirakc は修正版を自分で持つ

- 上流は 2024-10 から更新が無い。ホスト名対応と堅牢性の修正が必要(`facts.md` の F4)。
- 方向はフォーク。フォークの作成はユーザの作業なので、作成されるまではこのリポジトリ内のパッチ(`edcb/patches/bondriver/`)で進める。

## B. 設定の入口

### B1. 3 層に分ける

| 層 | 対象 | 適用のしかた |
|---|---|---|
| 環境変数 | コンテナ構成と一致が必要なもの、WebUI では変えられず初期設定に必須なもの | 指定されたキーを毎起動で上書き |
| 上書き用 ini | それ以外で、UI が無い・固定したいキー | 置かれたキーを毎起動で上書き |
| WebUI / EpgTimerNW | 日常の運用設定(録画マージン、プリセットなど) | 従来どおり EDCB が ini に書く。プロビジョニングは触らない |

- 理由: EDCB は WebUI から ini を自分で書き換える。テンプレートで毎回丸ごと上書きすると、WebUI での変更が消える。
- 運用設定を環境変数に写すことはしない(際限が無く、WebUI と衝突する)。

### B2. 既定値は「キーが無ければ書く」

- 初回かどうかを状態として持たず、キーが存在しないときだけ既定値を書く。既存の利用者の設定は変わらない。

### B3. 接続先は接続先ごとの環境変数で指定する

- `EDCB_BACKEND_<名前>_URL` の形。1 つの変数に詰め込む形にはしない。
- 理由: 接続先ごとの優先度やチューナー数の上書きが必要になるため。

## C. 後から変えにくいもの

### C1. BonDriver の命名

- 既定の接続先は `BonDriver_LinuxMirakc[_T|_S].so`(現在と同じ)。
- 追加の接続先は `BonDriver_LinuxMirakc_<名前>[_T|_S].so`。
- 接続先名に `T`、`S`、アンダースコアは使えない。
- 理由: ファイル名が ChSet4 のファイル名、`EpgTimerSrv.ini` のセクション名、チューナー固定予約に残るので、変えると移行が要る。

### C2. ボリュームの配置

- `./edcb/ini` → `/var/local/edcb` のマウントは変えない。
- 上書き用 ini は別ディレクトリ(`./edcb/overrides` → `/etc/edcb/overrides`、読み取り専用)。
- WebUI のファイル(`HttpPublic`)はイメージ側に置き、`HttpPublicFolder` で参照させる。ただし実行時に `HttpPublic` 配下へ書き込む処理が見つかった場合はボリュームに残す(判断基準は `design.md` の 6 章)。

### C3. 実行ユーザは PUID / PGID 方式

- コンテナは root で起動し、準備が済んだら `PUID` / `PGID` に権限を落として EDCB を実行する。
- compose の `user:` 指定は廃止する。`chmod 777` はやめる。

### C4. チューナー数の持ち主

- `[BonDriver_*.so]` セクションが無いときだけ自動で書く。以降、実際の本数と違っていたら警告するだけにする。
- 環境変数で本数を明示したときだけ、毎起動で強制する。

## D. 公開インターフェース

### D1. 既定のセキュリティ

- HTTP と TCP の ACL は、プライベートアドレス帯を既定で許可する。
- Legacy WebUI からの設定変更は、既定では禁止のまま。
- **許可と禁止は、コンテナを再起動せずに切り替えられること**(`edcbctl allow-setting on|off`)。環境変数は起動時の状態を決めるだけ。理由: 再起動は録画を中断する。現在の `chlegacyset.sh` も起動中に切り替えられる。

### D2. チャンネルスキャン

- チャンネル定義(`ChSet5.txt`)が無い初回だけ、起動時に自動でスキャンする。
- mirakc 側のチャンネル構成が変わったことを検知したら、警告だけ出す。自動で再スキャンはしない。
- 再スキャンは `edcbctl` で明示的に行う。

### D3. サポート範囲

- mirakc コンテナは同梱を続ける。使わない利用者は override で無効にできる。
- Mirakurun は、確認できた範囲で「対応」と書く。
- KonomiTV などは同梱しない。EDCB 側の既定(TCP 接続、ACL、視聴用設定)を整え、README に接続例を載せるまで。
- リバースプロキシも同梱しない。HTTPS は EDCB 自身の機能を、証明書を置けば有効になる形で提供する。

### D4. compose の扱い

- `compose.yml` を git 管理に入れる。利用者ごとの差分は `compose.override.yml` と `edcb.env` に置く(どちらも git 管理外)。
- 既存の利用者への移行案内は README に書く。自動移行の仕組みは作らない。

### D5. コンテナ名とボリューム名を固定しない

- `compose.yml` に `container_name` を書かない。名前付きボリュームに `name:` を書かない。どちらも Compose のプロジェクト名から決まるようにする。
- 理由: 同じホストで複数の構成(本番と検証用など)を並べられるようにするため。名前を固定すると、2 つ目の構成が起動に失敗するか、ボリュームを共有してしまう。
- 既存の利用者への影響は 2 点。コンテナ名が `edcb` から `<プロジェクト名>-edcb-1` に変わる。mirakc の EPG キャッシュ(`mirakc_epg`)は新しいボリュームに作り直される。どちらも移行手順に書く。
- 手順書では、コンテナ名ではなくサービス名で操作する(`docker compose exec edcb ...`)。

## E. 動作上の原則

### E1. 起動を止めない・遅らせない

- バックエンドに届かなくても EDCB は起動する。前回取得した情報で動かし、警告を出す。
- 時間のかかる処理(スキャン)で EpgTimerSrv の起動を待たせるのは、チャンネル定義が無い初回だけ。

### E2. 更新と再起動で録画を切らない

- 配布イメージは固定タグでの利用を勧める(`latest` と自動更新の併用を勧めない)。
- `stop_grace_period` を長めに設定する。
- 「録画中か、直近に予約があるか」を確認できるコマンドを用意する。

### E3. プロビジョニングは元に戻せる

- ファイルを書き換える前に退避を取る。
- 何を書き換えるかを事前に表示するモード(`--diff`)を持つ。
- 自分が生成したファイルだけを上書き・削除する。利用者が置いた・編集したファイルは触らず、警告する。

## F. pcscd

- コンテナ内蔵を既定にする。ホストのソケットがマウントされていれば、内蔵の pcscd を起動しない。

## G. ハードウェアエンコード

- 配布するイメージには、ベンダーのドライバ(Intel Media Driver など)を入れない。
- 配布イメージを `FROM` にして Intel のドライバを足す拡張用の Dockerfile を、見本として `edcb/hwaccel/intel/` に置く。利用者は `compose.override.yml` の `build:` で指定する。EDCB を自分でビルドし直す必要が無い。
- 見本は 2 段階にする。既定は Ubuntu のパッケージだけ(ffmpeg の `h264_qsv` / `h264_vaapi` 用)。QSVEncC は、ビルド引数でバージョンを指定したときだけ入れる。
- CI で見本のビルドだけを定期的に確認する。Intel 入りのイメージは公開しない。
- 現在の `edcb/Dockerfile` のコメントアウト部分(Intel Media Driver と QSVEncC)は、見本を作るフェーズ 5 で削除する。それまでは残す。
- 権限を落としたあとも `/dev/dri` を使えるようにする(`design.md` の 5 章の手順 6)。
- 理由: コメントアウト部分は QSVEncC の版が古く、すでに動かない。配布イメージを pull する利用者には使えず、ローカルビルドの利用者は Dockerfile を編集することになって `git pull` で衝突する。NVIDIA や AMD を使う利用者も、同じ形で拡張できる。
